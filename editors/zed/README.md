# Katlin for Zed

Language support for the [Katlin programming language](../../README.md) in
[Zed](https://zed.dev): syntax highlighting, bracket matching, indentation,
the outline panel, and **live compiler diagnostics**.

Zed needs its own kind of extension — it parses with tree-sitter rather than
the TextMate grammar used by the VS Code extension in `editors/vscode/` — so
this directory carries a grammar and the wiring to reuse the same language
server.

## Layout

```
editors/zed/
  extension.toml            generated by setup.sh (contains an absolute path)
  Cargo.toml                Rust extension crate
  src/katlin.rs             launches the language server
  languages/katlin/
    config.toml             language metadata: name, .ktl suffix, comments, brackets
    highlights.scm          syntax highlighting
    brackets.scm            bracket pairs
    indents.scm             auto-indentation
    outline.scm             outline panel

grammars/tree-sitter-katlin/
  grammar.js                the grammar
  src/                      generated parser
  test.sh                   verifies the grammar against every .ktl in the repo
```

## Installing

The extension is installed as a **development extension**, because Zed
resolves grammar repositories from the network and this grammar is bundled
locally.

```bash
# 1. Generate the parser (needs the tree-sitter CLI).
cargo install tree-sitter-cli --locked
cd grammars/tree-sitter-katlin && tree-sitter generate && cd -

# 2. Write extension.toml with the absolute path to the grammar.
editors/zed/setup.sh

# 3. In Zed: command palette -> "zed: install dev extension"
#    and select the directory:  editors/zed
```

Then open any `.ktl` file.

Building the Rust extension to WebAssembly needs the wasm target:

```bash
rustup target add wasm32-wasip2
```

## Configuration

Override the server command if your layout differs:

```json
{
  "lsp": {
    "katlin": {
      "binary": {
        "path": "/usr/bin/node",
        "arguments": ["/path/to/server.js", "/path/to/bin/katlin"]
      }
    }
  }
}
```

## What the diagnostics can and cannot tell you

The server is the same one the VS Code extension uses
(`editors/vscode/server/server.js`) — a dependency-free Node program speaking
LSP over stdio.

- **Front-end errors** — `#strict` borrow-checker violations, a missing
  `fn main` — carry a real source line and land on that line.
- **Backend errors** — type errors and the like — do not. The compiler emits
  C, clang reports positions in the generated `.build/<name>.c`, and there is
  no mapping back to the `.ktl` source. Rather than underline a line that
  might be wrong, these appear as one diagnostic at the top of the file with
  clang's message. `katlin check <file>` in a terminal gives the full context.

## Verifying

```bash
grammars/tree-sitter-katlin/test.sh    # 38 checks
```

Three layers:

1. **Parses every `.ktl` file in the repository** — including the compiler's
   own 2,800-line source and `examples/unsupported/`, which uses syntax the
   compiler cannot yet compile. Fails on any `ERROR` or `MISSING` node.
2. **Compiles each query file**, so a typo in a node or capture name fails
   here instead of silently dropping colour.
3. **Asserts specific captures land on specific text** (`fn` is `@keyword`,
   `Point` is `@type`, `Red` is `@variant`, ...). A bare "produced 341
   captures" check would still pass if every one of them were `@variable`.

The Rust extension is checked with:

```bash
cd editors/zed && cargo check
```

Note that this only type-checks; producing the actual `.wasm` needs
`rustup target add wasm32-wasip2`, which Zed uses when installing the
extension.

## Manual step

The last step — `zed: install dev extension` — is a GUI action and cannot be
scripted. Everything before it is automated.
